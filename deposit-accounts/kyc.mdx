# Customer KYC

Onboard your end-customer in the **customer vault** (`pcus_*`), then wait for `approved` before quoting with `customer_id`, and for `products.deposit_account.status=ready` before [opening accounts](/deposit-accounts/accounts). Full curl walkthrough: [Customers quickstart](/customers/quickstart).

<Note>
All calls use `X-API-Key` and `$BASE` (sandbox or live Partner API base). See [Authentication](/authentication).
</Note>

<Warning>
Do **not** start new integrations on `/partner/entities/*`. Those routes are transitional for older banking ops only.
</Warning>

## How KYC works

<Steps>
  <Step title="Read requirements">
    `GET /partner/customers/requirements?type=individual|business` (optional `country`). Collect exactly what it returns.
  </Step>
  <Step title="Create the customer">
    `POST /partner/customers` with `partner_customer_ref`, `type`, and `profile`. Save `data.id` (`pcus_*`).
  </Step>
  <Step title="Attach documents">
    `POST /partner/customers/{customer_id}/documents` (Base64 JSON). Categories come from requirements (e.g. `identity`, `address`).
  </Step>
  <Step title="Submit and wait">
    `POST …/submit` → typically `pending_review`. Element Pay reviews and approves on live. Poll `GET /partner/customers/{customer_id}` until `status=approved`.
  </Step>
  <Step title="Deposit-account product">
    After approve, check `products.deposit_account.status`. Open accounts only when `ready`. If `failed`, `POST …/deposit-account/retry`.
  </Step>
</Steps>

### Requirements

```bash
curl -sS "$BASE/partner/customers/requirements?type=individual" \
  -H "X-API-Key: $API_KEY" | jq '.data'

curl -sS "$BASE/partner/customers/requirements?type=business" \
  -H "X-API-Key: $API_KEY" | jq '.data'
```

### Documents you will need

Confirm against requirements before collecting:

| Type | Typical documents |
|------|-------------------|
| **Individual** | `identity` + `address` |
| **Business** | Company docs (`certificate_of_incorporation`, `memorandum_of_association`, `proof_of_address`, …) plus officer `identity` / `address` as listed |

### Business: single- vs multi-officer

| Path | Guidance |
|------|----------|
| **Single officer** | Prefer for first integrations |
| **Multi-officer** | Each officer needs distinct document uploads; do not reuse one PoA / same doc across officers |

### Retrieve a customer

```bash
curl -sS "$BASE/partner/customers/$CUSTOMER_ID" \
  -H "X-API-Key: $API_KEY" | jq '{
    id: .data.id,
    status: .data.status,
    partner_customer_ref: .data.partner_customer_ref,
    deposit_account: .data.products.deposit_account
  }'

curl -sS "$BASE/partner/customers?status=approved&limit=50" \
  -H "X-API-Key: $API_KEY" | jq '.data'
```

While `incomplete`, merge profile fields:

```bash
curl -sS -X PATCH "$BASE/partner/customers/$CUSTOMER_ID" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"profile": {"email": "updated@example.com"}}' | jq '.data'
```

## Individual create (sketch)

Required profile fields come from requirements. Typical individual package includes `first_name`, `last_name`, `email`, `date_of_birth` (**YYYY-MM-DD**), `country_of_residence`, `phone`, `gender`. Prefer `profile.address` for residential address.

```bash
curl -sS -X POST "$BASE/partner/customers" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "partner_customer_ref": "partner-cust-001",
    "type": "individual",
    "profile": {
      "first_name": "Jane",
      "last_name": "Doe",
      "email": "jane@example.com",
      "date_of_birth": "1990-01-15",
      "country_of_residence": "GB",
      "phone": "+447700900123",
      "gender": "f"
    }
  }' | jq '.data'
```

Upload docs, then submit — see [Customers quickstart](/customers/quickstart) for full curls.

## Business create (sketch)

```bash
curl -sS -X POST "$BASE/partner/customers" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "partner_customer_ref": "partner-biz-001",
    "type": "business",
    "profile": {
      "legal_name": "Acme Trading Ltd",
      "email": "treasury@acme.example",
      "phone": "+442071234567",
      "website": "https://acme.example",
      "business_type": "llc",
      "country_of_incorporation": "GB",
      "registered_address": {
        "line_1": "10 Business Park",
        "city": "London",
        "country_code": "GB",
        "postal_code": "EC2A 4BX"
      },
      "industry": "0763",
      "registration_number": "12345678",
      "description": "B2B payments for e-commerce merchants",
      "incorporation_meta": { "year": 2018, "month": 6, "country": "GB", "state": "England" },
      "monthly_payments_count": 100,
      "monthly_transaction_value": 50000,
      "max_transfer_amount": 10000,
      "annual_turnover": 600000,
      "customer_types": "businesses",
      "funding_source": "bank_account",
      "officers": []
    }
  }' | jq '.data'
```

Fill `officers` and documents per `GET …/requirements` before submit. US-incorporated businesses typically require `tax_id` (EIN) — requirements mark this when `country=US`.
