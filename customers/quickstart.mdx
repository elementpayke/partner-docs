# Customers quickstart

Onboard end-customers once into the **customer vault**, reuse a stable `customer_id` (`pcus_*`) on quotes, and open deposit rails when the deposit-account product is ready.

<Note>
Public identity is **`customer_id`** only. Legacy `/partner/entities/*` exists for older banking ops **do not adopt it for new integrations**. Customer-scoped sends, payouts, cards, and deposit-instructions are coming next (see [Roadmap](#roadmap)).
</Note>

## Two independent gates

| Gate | Condition | Unlocks |
|------|-----------|---------|
| **Orders** | `status=approved` | Quote / accept with `customer_id` |
| **Deposit accounts** | `products.deposit_account.status=ready` | `GET` / `POST` `/partner/customers/{customer_id}/accounts` |

Inline `customer` on `POST /partner/orders/quote` still works (require-`customer_id` flag is **not** enabled). Prefer `customer_id` for new integrations.

## Auth and environments

```bash
export BASE_SANDBOX="$BASE_SANDBOX"   # fill: sandbox Partner API base
export BASE_LIVE="$BASE_LIVE"         # fill: live Partner API base
export BASE="$BASE_SANDBOX"
export API_KEY="is_test_…"            # or is_live_… on live
```

```http
X-API-Key: <API_KEY>
Content-Type: application/json
```

Same partner `X-API-Key` as other `/partner/*` routes. Keys are per environment.

**Live:** after submit, Element Pay reviews and approves customers. Always read `status` from `GET /partner/customers/{customer_id}` — do not assume automatic approval on any environment.

## Status model

### Customer `status`

| Status | Meaning |
|--------|---------|
| `incomplete` | Profile / docs still being collected |
| `pending_review` | Submitted; waiting for Element Pay review |
| `approved` | Cleared for quote/accept with `customer_id` |
| `rejected` | Review declined |
| `suspended` | Blocked |

### `products.deposit_account.status`

| Status | Meaning |
|--------|---------|
| `none` | Banking profile not started |
| `provisioning` | Banking KYC in progress after EP approve |
| `ready` | May open / list / get accounts under this customer |
| `failed` | Provision failed — call [retry](#7-retry-deposit-account-if-failed) |
| `unavailable` | Product not available for this case |

`approved` alone does **not** unlock accounts.

## 1. Requirements

```bash
curl -sS "$BASE/partner/customers/requirements?type=individual" \
  -H "X-API-Key: $API_KEY" | jq '.data'

curl -sS "$BASE/partner/customers/requirements?type=business&country=US" \
  -H "X-API-Key: $API_KEY" | jq '.data'
```

Collect exactly the returned `required_fields` and `required_documents`.

## 2. Create customer

Idempotent on `partner_customer_ref` per tenant.

```bash
curl -sS -X POST "$BASE/partner/customers" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "partner_customer_ref": "partner-cust-001",
    "type": "individual",
    "profile": {
      "first_name": "Jane",
      "last_name": "Doe",
      "email": "jane@example.com",
      "date_of_birth": "1990-01-15",
      "country_of_residence": "GB",
      "phone": "+447700900123",
      "gender": "f",
      "address": {
        "line_1": "1 Example Street",
        "city": "London",
        "country": "GB",
        "postal_code": "E1 6AN"
      }
    }
  }' | jq '.data | {id, status, partner_customer_ref, missing}'
```

Save `data.id` (`pcus_*`). While incomplete: `PATCH /partner/customers/{customer_id}` with `{"profile": { … }}`. List: `GET /partner/customers?status=incomplete&limit=50`.

## 3. Upload documents

JSON + Base64. `category` must match a requirements document key.

```bash
export CUSTOMER_ID="pcus_…"

curl -sS -X POST "$BASE/partner/customers/$CUSTOMER_ID/documents" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "category": "identity",
    "file_name": "passport.pdf",
    "content_type": "application/pdf",
    "content_base64": "<BASE64>"
  }' | jq '.data'

curl -sS -X POST "$BASE/partner/customers/$CUSTOMER_ID/documents" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "category": "address",
    "file_name": "utility_bill.pdf",
    "content_type": "application/pdf",
    "content_base64": "<BASE64>"
  }' | jq '.data'
```

## 4. Submit

```bash
curl -sS -X POST "$BASE/partner/customers/$CUSTOMER_ID/submit" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{}' | jq '.data | {id, status, products}'
```

Incomplete package → **422** with `missing[]`.

## 5. Check status + deposit account

```bash
curl -sS "$BASE/partner/customers/$CUSTOMER_ID" \
  -H "X-API-Key: $API_KEY" | jq '{
    id: .data.id,
    status: .data.status,
    deposit_account: .data.products.deposit_account
  }'
```

Example (staging smoke, PII redacted):

```json
{
  "id": "pcus_06a83150db3c",
  "status": "approved",
  "deposit_account": { "status": "ready" }
}
```

| You need… | Wait until… |
|-----------|-------------|
| Quote with `customer_id` | `status == "approved"` |
| Open / list accounts | `products.deposit_account.status == "ready"` |

## 6a. Quote with `customer_id`

`payment_method` and `asset` remain required. Omit full inline `customer` when using `customer_id`. Accept is unchanged (`POST /partner/orders/{quote_id}/accept` with `{}`); identity is already on the quote when hydrated from the vault.

Amounts / networks / `network_id` are illustrative — discover `network_id` from payment-methods or catalog for the same `country` + `order_type`.

```bash
curl -sS -X POST "$BASE/partner/orders/quote" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "order_type": "OffRamp",
    "currency": "KES",
    "country": "KE",
    "local_amount": 100,
    "customer_id": "pcus_06a83150db3c",
    "asset": {
      "token": "0xc2132d05d31c914a87c6611c10748aeb04b58e8f",
      "currency": "USDT",
      "network": "POLYGON"
    },
    "payment_method": {
      "type": "mobile_money",
      "phone_number": "+2547XXXXXXXX",
      "network_id": "<FROM_CATALOG_OR_PAYMENT_METHODS>"
    }
  }' | jq '{quote_id: .data.quote_id, status: .data.status}'
```

Smoke outcome: success with `quote_id` like `ep_bank_…`. Use `asset: { token, currency, network }` — not a bare top-level `"token"`.

## 6b. Accounts (`deposit_account=ready` only)

```bash
curl -sS "$BASE/partner/customers/$CUSTOMER_ID/accounts" \
  -H "X-API-Key: $API_KEY" | jq '.data'

curl -sS -X POST "$BASE/partner/customers/$CUSTOMER_ID/accounts" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "asset_type": "fiat",
    "currency": "CAD"
  }' | jq '.data'

curl -sS "$BASE/partner/customers/$CUSTOMER_ID/accounts/$ACCOUNT_ID" \
  -H "X-API-Key: $API_KEY" | jq '.data'
```

Body fields: `asset_type`, `currency`, optional `network` (stablecoin), optional `display_name`. If rejected, see [API reference](/api-reference/introduction) rather than guessing.

Smoke: list with multiple rails; sample CAD account included `customer_id`.

## 7. Retry deposit account if `failed`

```bash
curl -sS -X POST "$BASE/partner/customers/$CUSTOMER_ID/deposit-account/retry" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{}' | jq '.data | {id, status, products}'
```

Best-effort; errors are partner-neutral. Re-GET until `ready`, or contact Element Pay if stuck on `failed` / `unavailable`.

## Errors

| Situation | Typical | Action |
|-----------|---------|--------|
| Missing profile/docs on submit | `422` + `missing[]` | PATCH / upload, resubmit |
| Quote with unapproved `customer_id` | `4xx` | Wait for `approved` |
| Accounts while not `ready` | `4xx` | Poll product; retry if `failed` |
| Unknown / other-tenant id | `404` | Use id from this API key |
| Bad key | `401` | Fix `X-API-Key` |

## Migration

| Phase | Behavior |
|-------|----------|
| **0 (now)** | Optional `customer_id`; inline `customer` still OK |
| **1** | New end-users get `pcus_*`; prefer `customer_id` on quote |
| **2** | Backfill repeat counterparties into the vault |
| **3 (later)** | Require `customer_id` via flag — **not enabled yet** |

## Roadmap

Facades resolve vault `customer_id` → bound banking profile → existing services. Nesting mirrors accounts: `/partner/customers/{customer_id}/…`.

| Increment | Scope |
|-----------|--------|
| **1 — Done** | Vault + accounts open/list/get + optional quote `customer_id` |
| **2 — Next** | Deposit-instructions, stablecoin sends, book transfers |
| **3 — Then** | Payouts, card issue/charge, remaining account-scoped ops |
| **4 — Later** | Deprecate `/partner/entities/{entity_id}/…` in docs, then API |

Do not build new integrations on `/partner/entities/*`.

## Not in this guide

- Wrapping all entity money ops under `customer_id`
- Requiring `customer_id` on all quotes
- Multi-provider KYC shopping
- Full accept → settlement E2E
- Admin UI beyond “Element Pay reviews and approves”

## FAQ

**Inline `customer` still OK?** Yes while the require flag is off. Prefer `customer_id` once approved.

**Approved but accounts fail?** Check `products.deposit_account.status` — must be `ready`.

**Use `/partner/entities` for new apps?** No.
