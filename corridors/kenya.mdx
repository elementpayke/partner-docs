# Kenya (KE / KES)

Kenya supports **M-PESA mobile money** and **bank** rails for OnRamp and OffRamp.

## Discovery

```bash
# OnRamp providers (momo + bank)
curl -sS "$BASE/partner/catalog?country=KE&order_type=OnRamp" \
  -H "X-API-Key: $API_KEY" | jq '.data.onramp.countries.KE'

# Field requirements (retail default)
curl -sS "$BASE/partner/order-requirements?country=KE&currency=KES&order_type=OnRamp" \
  -H "X-API-Key: $API_KEY" | jq '.data'

# Institution (B2B) field requirements
curl -sS "$BASE/partner/order-requirements?country=KE&currency=KES&order_type=OffRamp&customer_type=institution" \
  -H "X-API-Key: $API_KEY" | jq '.data'
```

## OnRamp (momo)

Customer pays KES via M-PESA → receives USDC/USDT on your `wallet_address`.

Full quote → accept with **`customer_id`**: [Quote and accept](/orders/quote-and-accept). End-to-end KYC first: [Quickstart](/quickstart).

## OffRamp (momo)

Use **Polygon USDT** on the quote:

| Field | Value |
|-------|--------|
| `asset.currency` | `USDT` |
| `asset.network` | `POLYGON` |
| `asset.token` | `0xc2132d05d31c914a87c6611c10748aeb04b58e8f` |

**Sandbox:** do **not** send crypto on-chain. Include **`Successful`** in `customer.name` and use success phone `+2541111111111` so the crypto leg auto-credits. Details: [Sandbox success & failure](/sandbox/success-failure).

**Production:** after accept, the customer sends the exact crypto amount to the deposit wallet in `data.accepted.payment_instructions.crypto_deposit` before `expires_at`.

1. Quote with `order_type: OffRamp`, `crypto_amount`, Polygon USDT `asset`, `refund_address`
2. Accept → for live, read `payment_instructions.crypto_deposit`
3. Sandbox: wait for webhook; production: customer sends exact amount before `expires_at`
4. Webhook `order.settled` when fiat is paid out to momo

<Warning>
On **EVM networks** (Base, Polygon) the OffRamp deposit address is **per order** from accept. Do not reuse across orders. Stellar behaves differently — see [OffRamp (Stellar USDC)](#offramp-stellar-usdc). Sandbox on-chain sends (e.g. testnet USDC/USDT) are not a supported settle path — use the `Successful` name trigger instead.
</Warning>

## OffRamp (Stellar USDC)

Kenya OffRamp also accepts **USDC on Stellar**, settling to M-PESA or bank in KES.

<Note>
This corridor is **enabled per environment**. While it is off, a quote with `asset.network: "STELLAR"` returns `422` and no Stellar row appears in the catalog. Confirm availability with Element Pay (`compliance@elementpay.net`) before building against it.
</Note>

Check your environment before integrating:

```bash
curl -sS "$BASE/partner/catalog?country=KE&order_type=OffRamp" \
  -H "X-API-Key: $API_KEY" | jq '.data.offramp.countries.KE.crypto_assets'
```

A `{"currency": "USDC", "network": "STELLAR"}` entry means the corridor is live for your key.

### Asset

| Field | Value |
|-------|--------|
| `asset.currency` | `USDC` (only — any other currency returns `422`) |
| `asset.network` | `STELLAR` |
| `asset.token` | **Omit.** Resolved server-side |

<Warning>
Do **not** hardcode a Stellar contract id. Unlike Base and Polygon, the USDC asset differs between sandbox and production, so the rail resolves it from `asset.network` instead. Sending an EVM-style `asset.token` here is the most common integration error.
</Warning>

### Supported rails

| `payment_method.type` | Payee fields | Settles via |
|-----------------------|--------------|-------------|
| `mobile_money` | `phone_number` | M-PESA |
| `bank` | `account_number`, `account_name` | Bank |

Both require `payment_method.network_id` — discover it from catalog or payment-methods with `order_type=OffRamp`. Do not hardcode it.

### Required quote fields

`currency`, `country: "KE"`, one of `crypto_amount` / `local_amount` / `fiat_amount`, `refund_address` (or `refund_to_source_address`), `payment_method.network_id`, and an approved `customer_id`. Bank adds `account_number` + `account_name`; momo adds `phone_number`. Anything missing returns `422` with `data.missing_fields`.

```bash
curl -sS -X POST "$BASE/partner/orders/quote" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "order_type": "OffRamp",
    "country": "KE",
    "currency": "KES",
    "crypto_amount": 25,
    "asset": { "currency": "USDC", "network": "STELLAR" },
    "customer_id": "pcus_...",
    "refund_address": "G...",
    "payment_method": {
      "type": "mobile_money",
      "network_id": "<from catalog>",
      "phone_number": "+2541111111111"
    }
  }' | jq '.'
```

### Deposit instructions — memo is mandatory

Accept returns `data.accepted.payment_instructions` with a **shared** Stellar address and a per-order memo:

```json
{
  "type": "crypto_deposit",
  "wallet_address": "G...",
  "amount": "25.0000000",
  "currency": "USDC",
  "network": "STELLAR",
  "memo": "EP3f2a9c1b7d4e6f8a0b2c4d",
  "memo_type": "text",
  "expires_at": "2026-11-16T14:05:00Z",
  "note": "Send the exact USDC amount to this address and include the memo."
}
```

<Warning>
The Stellar deposit address is **shared across orders** — the `memo` is the only thing that identifies the payment. A deposit sent without the exact `memo` (type `text`) cannot be matched to an order, will not auto-credit, and needs manual recovery. Always pass `memo` through to the sending wallet.
</Warning>

Settlement notes:

- **7 decimals** on Stellar, not the 6 used by Base and Polygon. Send the exact `amount`; a short payment fails the order.
- Deposits are matched by polling Horizon, so credit is not tied to EVM-style block confirmations.
- Quotes expire in **15 minutes**; the deposit window after accept is **3 hours** (`expires_at`).
- Webhooks are unchanged: `order.processing`, `order.settled`, `order.failed`, `order.refunded`.

<Note>
[Signed accepts](/orders/signed-accepts) are **EVM-only** and cannot be used on this corridor. Accept Stellar quotes with the standard `customer_id` flow.
</Note>

## Bank rail

Use `payment_method.type: bank` and `network_id` from payment-methods (preferred) or catalog. Provider lists differ by direction — look up with the same `country` and `order_type` as the quote (do not reuse an OnRamp id on OffRamp).

```bash
curl -sS "$BASE/partner/payment-methods?country=KE&order_type=OnRamp" \
  -H "X-API-Key: $API_KEY" | jq .

curl -sS "$BASE/partner/payment-methods?country=KE&order_type=OffRamp" \
  -H "X-API-Key: $API_KEY" | jq .

# Also in catalog under payment_methods.bank.providers[] (filter catalog by the quote’s order_type)
curl -sS "$BASE/partner/catalog?country=KE&order_type=OnRamp" \
  -H "X-API-Key: $API_KEY" | jq '.data.onramp.countries.KE.payment_methods.bank.providers'
```

For momo, use catalog or payment-methods only — **`GET /partner/banks` returns 422 for `mobile_money`** and is not the primary path for African local fiat bank institutions.

## Institution (B2B)

Same OnRamp/OffRamp quote body as retail; set `customer_type: "institution"` and `customer.type: "institution"`. Required customer fields: `uid`, `business_name`, `business_id`, `email` — no DOB, national ID, or personal `name`. `business_id` is the paying business’s legal registration/tax id (not an Element Pay console id).

For bank rails, the payee is `payment_method.account_name` + `account_number` + `network_id` (payee company may differ from the paying business). Discover exact fields with `customer_type=institution` on order-requirements (above). Copy-paste OffRamp bank example: [Sandbox test payloads](/sandbox/test-payloads).
